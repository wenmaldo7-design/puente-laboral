## Technical Approach

The implementation will span the entire stack, from database seeding to frontend visualization. A new backend module (`AdminReportsModule`) will provide endpoints to aggregate the required metrics (active job offers, accepted candidates, match percentage) using direct Prisma queries, applying time-based filters. The frontend will introduce a new `admin` feature module containing the Dashboard component, which will fetch these metrics and handle empty states. The login routing will be updated to direct admin users to this new dashboard. File exports (Excel/PDF) will be generated by the backend to ensure data consistency and offload processing from the client.

## Architecture Decisions

### Decision: Backend vs Frontend Metrics Calculation
**Choice**: Backend metrics calculation.
**Alternatives considered**: Fetch all raw job and candidate data and calculate on the frontend.
**Rationale**: Fetching all active jobs and candidates to the frontend for calculating the match percentage would transfer too much data and be too slow. The backend can execute efficient aggregations directly in PostgreSQL via Prisma.

### Decision: File Export Generation (Excel/PDF)
**Choice**: File generation on the backend.
**Alternatives considered**: Generate files on the frontend using libraries like `xlsx` or `jspdf`.
**Rationale**: Generating official reports on the backend is generally safer, ensures data integrity, and keeps frontend bundles smaller. The backend will expose endpoints that stream the generated Excel or PDF files based on the requested time filter.

### Decision: Admin Authentication and Routing
**Choice**: Update `login-page.ts` to route admin users to `/admin/dashboard`.
**Alternatives considered**: Keep admins on `/empresas/solicitudes` or create a separate login view.
**Rationale**: The proposal explicitly requests routing admins to the new dashboard upon login, seamlessly integrating with the existing role-based authentication flow.
